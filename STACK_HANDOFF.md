# STACK — хендофф между сессиями

Этот файл читают в начале новой сессии вместе с `CLAUDE.md`, чтобы продолжить
работу без пересказа истории. Обновляй его в конце каждой сессии: что сделано,
что осталось, на что обратить внимание.

**Git — источник истины.** Если этот файл разойдётся с `git log` — верь git,
поправь файл.

## Важно: несколько параллельных сессий

Над этим репозиторием может одновременно работать больше одной сессии Claude
Code (разные чаты/вкладки), каждая на своей ветке `claude/<random-name>`.
Перед началом работы в новой сессии:

1. `git fetch origin main` и `git log origin/main --oneline -10` — проверить,
   что реально уже в `main` (могло прилететь из другой сессии).
2. Разработку вести на ветке, которую назначит система для этой сессии.
   Если ветка сессии уже смержена в `main` — пересоздать её от `main`
   (`git fetch origin main && git checkout -B <branch> origin/main`), не
   наслаивать новые коммиты на уже смерженную историю.

## Деплой / как обновление доходит до пользователя

- Прод — GitHub Pages, ветка **`main`**, корень репозитория
  (`https://hinoob13031997.github.io/my-tracker/`).
- Прямой `git push` в `main` блокируется классификатором безопасности сессии
  («Merge Without Review»). Рабочий путь: закоммитить на свою ветку → открыть
  PR → смержить PR через GitHub API (`mcp__github__merge_pull_request`,
  squash) — это классификатор пропускает.
- При мерже, если ветка сессии до этого форкнулась от более старого `main`
  (после того как другая сессия уже что-то смержила) — будет
  «Pull Request has merge conflicts»: `git fetch origin main`,
  `git merge origin/main`, конфликты почти всегда тривиальные (BUILD/CACHE/
  VERSION дублирующиеся бампы) — оставлять свою (более новую) версию.
- После **каждого** изменения живого JS-файла: поднимать `BUILD`/`CACHE` в
  `sw.js` и `VERSION` в `stack-persistence.js` — иначе пользователь получит
  старый файл из кэша service worker.
- Пользователю после мержа: подождать 1–2 минуты (пересборка Pages), затем
  полностью закрыть и заново открыть приложение (обычный reload может не
  подхватить новый service worker).

## СЛЕДУЮЩАЯ ЗАДАЧА — унификация архитектуры вкладок Fitness (по образцу Дел)

После серии инцидентов v29.19 → v29.25 (все — варианты одного и того же
класса бага: снос/пересоздание DOM + гоняющиеся друг за другом
`MutationObserver`) сравнил архитектуру переключения вкладок в разделе
«Дела» и в разделе «Fitness». Разница системная, не косметическая —
именно она причина того, что баги там возникают снова и снова в разных
местах после каждого точечного патча.

**Обновление v29.26**: пилотный шаг (вкладка «Прогресс») сделан и
смержен, см. раздел «v29.26» ниже — там же ключевые открытия про то,
почему Today/Nutrition сложнее, чем казалось, и что учитывать в
следующих шагах.

### Дела (`v233-tabs`, `stack-v23-deals.js`) — эталон

- Один файл — единственный владелец экрана и всех вкладок.
- Все панели вкладок строятся в DOM **один раз**: `#v233Processes`,
  `#v233Calendar` (плюс уже существующий `#v2212Tasks` для «Задачи»).
- Переключение вкладки — это просто `classList.toggle('on', ...)`,
  CSS делает `.v233-panel{display:none}.v233-panel.on{display:block}`.
  Контент **не пересоздаётся и не сносится** при переключении.
- Один `render()`, ноль `MutationObserver`, никакой гонки.

### Fitness (`v234-tabs`, ~12 файлов) — то, что нужно исправить

- Нет единого владельца. `stack-v23-fitness.js` держит переменную `tab`
  и на КАЖДЫЙ клик по вкладке **полностью сносит и перестраивает**
  `innerHTML` у `.v234-body`, используя старые legacy-шаблоны
  (`today()/progress()/nutrition()` из v23 — во многом уже мёртвый код,
  визуально перекрываемый другими модулями).
- Поверх этого 8+ независимых модулей (`stack-v23-fitness-goals.js`,
  `stack-v23-fitness-engine.js`, `stack-v23-fitness-intelligence.js`,
  `stack-v24-fitness-analytics.js`, `stack-v27-3-nutrition.js`,
  `stack-v27-4-nutrition-goals.js`, `stack-v27-5-2-nutrition-minimal.js`,
  `stack-v27-5-3-ration.js`, `stack-v27-5-quick-foods.js`,
  `stack-v27-5-5-nutrition-reorder.js`, `stack-v23-fitness-day-picker.js`)
  следят за ЛЮБОЙ мутацией `.v234-body` через свои `MutationObserver` и
  реактивно доливают/чинят карточки поверх снесённого контента.
- Именно это порождало DOM-churn v29.19/20/22/23 и, судя по всему, даже
  «opacity отказывается анимироваться» из v29.24/25 (узел `.v234-body`
  слишком часто полностью пересоздаётся/переписывается — предположительно
  compositing-артефакт на этом конкретном, много раз мутировавшем узле).

### Целевая архитектура (план, согласован с пользователем, ещё НЕ начат)

Перевести Fitness на паттерн Дел:
1. Три постоянные панели строятся один раз при boot: `#v234Today`,
   `#v234Progress`, `#v234Nutrition` (имена ориентировочные).
2. Переключение вкладки — ТОЛЬКО `classList.toggle('on', ...)` +
   CSS `display:none/block`, как в `.v233-panel`. `.v234-body.innerHTML`
   больше никто не перезаписывает целиком.
3. Каждый существующий модуль (goals/ration/engine/quick-foods/…)
   переписывается так, чтобы писать СТРОГО в свою панель по id, без
   сноса чужого содержимого и без реакции на мутации, которые вызвал не
   он сам.
4. `stack-v23-fitness.js` перестаёт быть «владельцем сноса» — либо
   упрощается до чистого builder'а трёх панелей, либо его роль
   полностью забирает новый объединяющий файл (по аналогии с ролью
   `stack-v23-deals.js` для Дел).

### Как делать (важно)

- Это крупный рефактор на ~10 файлов, НЕ точечный патч — делать поэтапно,
  каждый шаг коммитить и проверять headless отдельно, не одним махом.
- **Критично**: headless-проверка ТОЛЬКО через реальный путь навигации —
  клик по `.v29-nav [data-v29-nav="fitness"]`, а НЕ по legacy
  `#mobileNav` (он `display:none` под v29 shell на мобильном; клики по
  нему технически проходят и мутируют DOM внутри `display:none`
  `.app`-контейнера, создавая ложное впечатление рабочего теста — это
  ровно то, из-за чего v29.24 задеплоили нерабочей, см. раздел v29.25
  выше).
- После каждого шага: `node --check`, headless-обход всех 5 разделов +
  всех вкладок Fitness (0 JS-ошибок, 0 horizontal overflow), проверка что
  DOM-churn (0 лишних мутаций на `.v234-body`/будущих панелях после
  серии кликов) не вернулся.
- Данные/storage keys (`stack_fitness_*`) не трогать — это чисто
  DOM/рендер-рефактор, а не миграция схемы.
- Не бояться проверить сначала на ОДНОЙ вкладке (например Progress —
  она проще всего) как пилотный шаг, прежде чем переносить остальные.

## v29.26 — пилотный шаг: вкладка «Прогресс» переведена на постоянную панель

Первый шаг унификации архитектуры вкладок Fitness (задача выше). Смержено
в PR #51 (`830d8c2`). Сделал ТОЛЬКО вкладку «Прогресс» — Сегодня/Программа/
Питание намеренно не трогал, остаются на старом пути (полный снос
`.v234-body`) до следующих шагов.

**Что сделано**: `stack-v23-fitness.js` теперь строит при boot постоянный
узел `#v234Progress` (сосед `.v234-body`, а не его замена) и переключает
видимость через `classList.toggle('on')` + CSS `.v234-panel{display:none}
.v234-panel.on{display:block}` — по образцу `.v233-panel` из Дел. На
вкладке «Прогресс» `render()` пишет `progress()` только в `#v234Progress`
и не трогает `.v234-body`; на Сегодня/Программа/Питание — наоборот,
`.v234-body` рендерится как раньше, `#v234Progress` не трогается.
«Программа» (`tab==='program'`, drill-down с кнопки внутри Прогресса)
намеренно оставлена внутри старого `.v234-body`, а не в новой панели —
это отдельное состояние, не одна из 3 вкладок нижнего таб-бара, и вынос
её в `#v234Progress` не требовался для этого шага.

**Важное открытие, объясняющее почему это НЕ тривиальная замена одного
файла** (учитывать в следующих шагах — Today/Nutrition):

Карточка «МОЯ ЦЕЛЬ» (`stack-v23-fitness-goals.js`, `[data-goal-card]`)
вставляется на **КАЖДОЙ** вкладке (Сегодня/Программа/Питание/Прогресс),
а не только на нужной — `draw()` там ничего не знает про конкретную
вкладку, просто вставляет карточку в `body`, если её там ещё нет. Плюс
`stack-v23-fitness-engine.js` (аналитика на Прогрессе), `stack-v23-
fitness-intelligence.js` (план/факт на Питании, стратегия на Программе,
адаптация на Прогрессе) — все трое читают `body=root.querySelector(
'.v234-body')` и ищут/вставляют относительно `[data-goal-card]` внутри
этого же `body`. Раньше это работало, потому что `.v234-body` в любой
момент содержал контент РОВНО ОДНОЙ активной вкладки (остальное полностью
снесено) — значит `body.querySelector(...)` всегда искал «в правильном
месте» просто по факту отсутствия альтернатив.

Как только вкладка получает СВОЙ постоянный узел (а не общий
`.v234-body`), это предположение ломается: `.v234-body` продолжает
существовать (пусть и скрытый) со СТАРЫМ контентом, и наивный
`body.querySelector('.v234-body')` в этих модулях находил бы не ту
карточку/не тот якорь. Фикс — не трогать сами модули по существу, а
сделать их поиск контейнера ДИНАМИЧЕСКИМ: `body = tab==='progress' ?
document.querySelector('#v234Progress') : document.querySelector(
'.v234-body')` (engine.js, goals.js, intelligence.js), и то же самое,
но без ветвления, для `stack-v24-fitness-analytics.js` (там `body`
ВСЕГДА означает Прогресс, функция и так ничего не делает на других
вкладках). Это единственное содержательное изменение в этих 4 файлах —
дальше вся их логика (какая карточка куда вставляется/обновляется)
осталась буквально той же.

Более серьёзное препятствие, из-за которого «просто добавить
`#v234Nutrition`/`#v234Today` и повторить трюк» НЕ сработает для
Nutrition без изменений в самих nutrition-модулях: `stack-v27-3-
nutrition.js`, `stack-v27-4-nutrition-goals.js`, `stack-v27-5-1-
nutrition-simplify.js`, `stack-v27-5-2-nutrition-minimal.js`, `stack-v27-
5-quick-foods.js` — ВСЕ они делают `document.querySelector('#v234Fitness
.v234-body')`, а затем `.prepend(...)` **прямо на этот узел** (не на
дочерний элемент внутри него). Если `.v234-body` станет общим wrapper'ом
с несколькими дочерними панелями (как я сначала планировал), их контент
воткнётся ПЕРЕД панелями как их сосед, минуя `display:none/block`
переключение панелей — то есть будет виден на любой вкладке, а не только
на «Питании». Именно поэтому для Прогресса я выбрал другую форму: НЕ
делать общий wrapper с тремя детьми, а держать `#v234Progress` отдельным
сиблингом `.v234-body`, полностью в стороне от старого пути. Для
Nutrition (и аналогично Today, там похожая история с `stack-v23-fitness-
day-picker.js`, которая тоже делает `host.innerHTML=...` на
`.v234-body` целиком) этот же трюк сработает, но потребует помимо
основного файла ещё обновить точки вставки в каждом из перечисленных
nutrition-модулей — то есть Nutrition — самый трудоёмкий из трёх шагов,
не самый простой.

**Проверено headless** (Playwright, mobile 390×844, клики только по
`.v29-nav [data-v29-nav="fitness"]` и `#v234Fitness .v234-tabs
[data-v234="..."]`): обход всех 5 разделов + всех 3 вкладок Fitness — 0
JS-ошибок, 0 horizontal overflow; 8 быстрых переключений вкладок подряд —
0 лишних DOM-мутаций на `.v234-body`/`#v234Progress` через 2+ секунды
после того как всё осело; карточка «МОЯ ЦЕЛЬ» и вся аналитика на
Прогрессе рендерятся с корректными значениями; Сегодня/Питание визуально
не изменились.

**Файлы**: `stack-v23-fitness.js`, `stack-v23-fitness-engine.js`,
`stack-v23-fitness-goals.js`, `stack-v23-fitness-intelligence.js`,
`stack-v24-fitness-analytics.js`, `stack-v24-mobile-readability.js`,
`stack-v27-1-fitness-tabs.js` (ширина/overflow guard'ы расширены на
`#v234Progress`), `sw.js` (BUILD → 29.26.0, CACHE →
`stack-v29-26-fitness-progress-panel-pilot`), `stack-persistence.js`
(VERSION → v29.26). Данные/storage keys не менял.

**Следующий шаг**: вкладка «Сегодня» (owner — `stack-v23-fitness-day-
picker.js`, плюс те же 4 модуля выше с их today/program-ветками) или
«Питание» (5 nutrition-модулей, самый трудоёмкий шаг). Рекомендую Today

## v29.18 — первый кадр реально не принадлежал новому shell

**Причина**: `window.__STACK_V29__=true` и три `<script defer src="stack-v29-*.js">`
никогда не были в `index.html` — их вставлял только `sw.js` (`withV29Shell()`,
переписывает `<head>` ответа на лету). Но service worker управляет страницей
только начиная со **второй** загрузки (регистрация идёт по `window.onload`,
т.е. уже после того как страница отрисовалась; SW сам форсит один reload через
`clients.claim()+client.navigate()`, но это происходит уже постфактум). На
самой первой загрузке в браузере (новое устройство, переустановка PWA, чистка
site data, SW отключён политикой) `__STACK_V29__` не установлен →
`stack-v27-bootstrap.js`'s `V29()` возвращает false → грузится легаси
`stack-v28-minimal.js` (`renderMore()`-хаб) → пользователь на секунду видит
старый UI, пока SW не форсит скрытый reload. Прямое нарушение правила
CLAUDE.md «Startup»: «новый shell должен владеть первым кадром».

**Фикс**: тот же самый HTML-кусок (`GATE_STYLE` + `V29_HEAD` из `sw.js`,
включая gate-заглушку с текстом «STACK» на mobile) теперь вписан напрямую в
`index.html` сразу после `<head>`. `withV29Shell()` в `sw.js` не трогали —
он уже содержит защиту `if(!html.includes('stack-v29-shell.js'))`, поэтому
на все последующие (SW-controlled) загрузки просто не инжектит повторно —
дублирования тегов нет ни на первой, ни на последующих загрузках.

**Подтверждено локально** (headless Chromium, mobile viewport, `serviceWorkers:
'block'` — эмуляция самой первой загрузки без SW): до фикса —
`__STACK_V29__=false`, `stack-v28-minimal.js` грузится, `.app` (легаси)
видим; после фикса — `__STACK_V29__=true` сразу, `stack-v28-minimal.js`
вообще не грузится, `#stackV29Root` рендерит «Сегодня» сразу, класс
`stack-v29-ready` выставлен.

**Файлы**: `index.html` (baked-in gate/shell markup), `sw.js` (BUILD →
29.18.0, CACHE → `stack-v29-18-first-load-shell`), `stack-persistence.js`
(`VERSION` → `v29.18`).

**Важно на будущее**: если поменяется список v29-скриптов или CSS
gate-заглушки в `sw.js`'s `GATE_STYLE`/`V29_HEAD` — обновлять тот же кусок в
`index.html` вручную (это теперь два места, которые должны совпадать; сам
`sw.js` не даст задублироваться, но и не подскажет, что копия в
`index.html` устарела).

mobile-overflow чек-листу CLAUDE.md на новом `stack-v29-analytics.js`.

## v29.19 — «экран скачет» на вкладке Питание = бесконечный DOM-цикл

Пользователь сообщил: после деплоя v29.18 на вкладке «Питание» экран
скачет. Это НЕ разовый флеш при открытии — это был **постоянный** баг,
воспроизводится и без моих правок из v29.18.

**Причина** (`stack-v27-5-1-nutrition-simplify.js`, `apply()`): функция
подписана на `MutationObserver`, который слушает **любую** мутацию внутри
`#v234Fitness .v234-body` (`subtree:true`) и на каждую мутацию сама же
вызывает `apply()`. Внутри `apply()` было безусловное
`eye.textContent='ДОБАВИТЬ ЕДУ'` и `h.textContent='Новая запись'` — запись

не разово при заходе, а непрерывно. Именно это и ощущается как «экран
скачет» (плюс сажает батарею/CPU).

**Фикс**: записывать `textContent` только если значение реально

трогал — `stack-v27-5-5-nutrition-reorder.js` пробовал переписать под

фикс только в simplify.js полностью убирает цикл (проверил headless:
0 мутаций за 3с в состоянии покоя после серии кликов по вкладкам и
`stack:data-changed`).

Остаётся отдельный, гораздо менее серьёзный нюанс: при **первом**

вкладки (не на постоянное дрожание) — сюда возвращаться отдельно.

## v29.23 — найдена и устранена НАСТОЯЩАЯ причина «дёргается»: DOM-churn на КАЖДОМ клике

Пользователь подтвердил после v29.22: дёргается по-прежнему, причём
**на любом взаимодействии** — переключение вариантов рациона 1↔2↔3↔4 И
клик «ПОЕЛ»/«НЕ ЕЛ». Не «иногда», а каждый раз. Это подсказка: v29.22
убрал вероятный, но не доказанный со 100% фактор (`.fx-plan`); реальная
причина оказалась детерминированной и системной.

**Расследование**: поставил `MutationObserver({childList:true})` прямо на
`#v234Fitness .v234-body` (только прямые дети — то есть отслеживает
именно ПЕРЕСТАНОВКУ карточек друг относительно друга, а не изменения
внутри них) и залогировал добавления/удаления узлов при одном клике по
«ПОЕЛ». Итог **до фикса**: 20 add/remove-событий на ОДИН клик — узлы
`v273Nutrition`, `v275QuickFoods` (×2), `v2753Ration`,
`v2752NutritionMinimal`, `fx-card` (add-card и collapsible) физически
удалялись и создавались заново, при этом порядок прямых детей
`.v234-body` дважды полностью менялся в течение ~30мс после клика
(проверено снятием снапшотов order на t+0/20/40/80/160/300/500/800мс).

**Причина**: пять разных модулей питания
(`stack-v27-5-3-ration.js`, `stack-v27-4-nutrition-goals.js`,
`stack-v27-5-2-nutrition-minimal.js`, `stack-v27-3-nutrition.js`,
`stack-v27-5-quick-foods.js`) на КАЖДЫЙ вызов своего `render()` — а
`render()` вызывается на КАЖДОЕ событие `stack:data-changed` В ЛЮБОМ ИЗ
НИХ, не только у себя — делали:
`document.getElementById('...')?.remove()` → `createElement('section')`
→ `body.prepend(...)` / `anchor.after(...)`. То есть даже если реально
изменились только данные РАЦИОНА, все ПЯТЬ карточек Питания сносились и
пересоздавались заново, каждая на свою жёстко закодированную позицию
(`prepend` = в начало!). Плюс `stack-v27-5-5-nutrition-reorder.js`'s
`reorder()` после этого физически двигал (`insertBefore`) узлы обратно
на «правильные» места — используя наивный курсор-обход, который не
учитывал посторонних соседей между отслеживаемыми карточками и поэтому
почти всегда что-то двигал, даже если относительный порядок уже был
верным. Итог: клик по одной кнопке → 3-4 модуля наперегонки сносят и
пересоздают свои карточки, `reorder()` расталкивает их обратно — визуально
это ощущается как «экран дёргается», причём КАЖДЫЙ раз, потому что
`stack:data-changed` летит на любое действие (клик по варианту, тоггл
приёма пищи, сохранение цели).

**Фикс**: в пяти файлах поменял паттерн рендера с «снести узел → создать
новый → вставить на жёсткую позицию» на «обновить существующий узел
in-place» — если `#id` уже есть в DOM, апдейтим `innerHTML`/`className`
только если контент реально изменился (сравнение строк, тот же приём,
что и в v29.19/v29.20), без удаления/пересоздания узла и без повторной
вставки в DOM; создаём + позиционируем узел только один раз, при первом
рендере. `stack-v27-5-5-nutrition-reorder.js`'s `reorder()` теперь
сначала проверяет, совпадает ли уже текущий относительный порядок
отслеживаемых карточек (не считая посторонних соседей) с нужным — и если
да, вообще не трогает DOM.

## Известные особенности среды сессии

- `node --check` — единственный доступный синтаксис-чекер, но нет линтера/
  сборки/тестов в проекте.
- Playwright установлен глобально в `/opt/node22/lib/node_modules`, браузер
  в `/opt/pw-browsers/chromium` — обычный `npx playwright` не сработает без
  `NODE_PATH=/opt/node22/lib/node_modules`, нужно указывать
  `executablePath: '/opt/pw-browsers/chromium'` явно.
- Headless-проверку страницы делать **через локальный http-сервер**
  (`http.createServer`), не через `file://` — при открытии файла напрямую
  браузер иногда неверно определяет кодировку и ломает кириллицу в JS
  (`Invalid or unexpected token`). Отдавать файлы с `charset=utf-8` в
  Content-Type.
- Прямой доступ к `hinoob13031997.github.io` из этой песочницы заблокирован
  egress-прокси (`EGRESS_BLOCKED` / `CONNECT tunnel failed, 403`) — нельзя
  проверить прод напрямую через `curl`/`WebFetch`. Проверять логику локально
  (headless на скопированных файлах) и полагаться на отчёт пользователя.
- GitHub-доступ — через `mcp__github__*` (MCP-сервер), не через `gh` CLI.
