# STACK — руководство для Claude Code

STACK — персональная система управления жизнью и работой (не habit tracker).
Идея: не планировать жизнь, а видеть, куда она реально движется.

Домены: процессы, задачи, Fitness, питание, финансы, аналитика, фактическая
траектория пользователя.

Продуктовая логика:
- **Сегодня** — что делать;
- **Раздел** — куда внести данные;
- **Аналитика** — что данные означают.

## Роль

Действуй как ведущий frontend/product engineer проекта, а не консультант.
Если задача понятна: находишь файлы → разбираешь архитектуру → находишь
реальную причину → вносишь исправление → проверяешь → даёшь короткий итог.
Не останавливайся на объяснении, если можешь исправить. Не спрашивай
подтверждение на мелочи. Спрашивай пользователя, только если решение влияет
на структуру/удаление данных, крупную UX-концепцию или необратимое действие.

## Архитектурная цель: STACK 2.0 / v29

Идёт постепенный переход на новую архитектуру. Нельзя бесконечно наращивать
старые DOM-патчи поверх legacy UI — новая архитектура должна становиться
владельцем интерфейса.

Целевая мобильная навигация (5 пунктов): **Сегодня / Дела / Fitness /
Финансы / Аналитика**.

Модули v22–v28 могут оставаться источником данных/бизнес-логики, но их UI
нужно постепенно выводить из эксплуатации — не плодить новый слой поверх
старого, а переносить экраны в v29-shell и удалять legacy-разметку под ними.

Ключевые файлы v29:
- `stack-v29-shell.js` — мобильный shell, Today, нижняя навигация, History
  API, переходы между новыми/legacy разделами.
- `stack-v29-deals-polish.js` — только визуальная полировка раздела «Дела»,
  без бизнес-логики.
- `sw.js` — cache/build, внедряет новый shell раньше legacy UI.

## Данные нельзя ломать

Проект уже используется с реальными данными.

**Не делать**: сброс localStorage, изменение существующих storage keys без
необходимости, удаление пользовательских данных, массовую миграцию схемы
без явной причины, «очистку» данных ради UI-фикса, параллельное состояние
вместо существующего. Сохранять обратную совместимость. Если меняешь
структуру данных — сначала докажи необходимость.

### Storage / data contracts

Основное состояние: `stack_neon_mix9_calendar_v1`

Nutrition:
- `stack_fitness_goal_v2318`
- `stack_fitness_profile_v2320`
- `stack_fitness_log_v2310`
- `stack_fitness_nutrition_v2310`
- `stack_fitness_nutrition_plan_v2311`
- `stack_fitness_nutrition_variant_v241`
- `stack_nutrition_targets_v274`
- `stack_nutrition_quick_foods_v275`
- `stack_nutrition_swaps_v2968` — замены продуктов в рационе (v29.68)

Финансы, месячный ввод: `stack_income_tracker_v1` = `{values, expenses, reserve}`, в каждом
карта `'YYYY-MM' → сумма`; **доход лежит в `values`** (его читают `STACK_FINANCE` и годовой вид).
Живой ввод — `stack-v25-finance.js`; `v22.3-income.js` (скрытый легаси-экран) пишет только
точечно — read-modify-write одной ячейки поверх сохранённого значения. Модуль никогда не пишет
ключ целиком из своей копии в памяти: так стирались введённые на живом экране значения при
сворачивании приложения (v29.90). Это правило для любого модуля с копией данных в памяти.

Сохранение (v29.81): `save()` (`index.html`) возвращает `true` только если основной
ключ реально записан — тост «Сохранено» и любой вызывающий код должны опираться на
это, а не на «вызов не упал». Ревизия `state._meta.revision` растёт **в самом `save()`**
и должна оставаться монотонной при загрузке/импорте/восстановлении (иначе `reconcile`
в `v22.2.js` примет более старую копию IndexedDB за новую и откатит данные); при
замене `state` целиком переносить `_meta` (см. импорт и `adopt()` в
`stack-persistence.js`). Копия в IndexedDB (`stack_state`) пишется отложенно
(`idbSaveSoon` / `idbFlush`), не на каждый тап. Подмешивание «недостающих ключей из
прошлой копии» при сохранении убрано — оно воскрешало удалённые поля.

Точки восстановления (v29.81, `stack-persistence.js`, `STACK_RECOVERY`): записи
`snap:<ts>` + `snapm:<ts>` в существующем IndexedDB-хранилище (DB не обновлялась).
Хранится самое новое состояние за 15 минут (до 2 ч), за день (14 дней), за месяц
(~6 мес.); точки `before-import / before-restore / before-delete` закреплены на 14
дней. Точка = основное состояние + сырые `stack_*` ключи (как полный бэкап).
Пустое состояние (`STACK_DATA.hasData`) в точки не пишется. Интерфейс —
Аналитика → «Данные» → «Точки восстановления». Старые списки
`stack_recovery_v2242` / `stack_backups_v21` больше не пишутся, только читаются.
Перед любым новым деструктивным действием (удаление процесса/задачи/операции,
импорт) вызывать `STACK_RECOVERY.snapshotNow('before-…')`.

Напоминание о копии (v29.81): `stack_backup_meta_v1` `{since,last}` — когда скачан
последний файл; в бэкап не входит. Через 14 дней без файла «Сегодня» и «Аналитика»
показывают строку-напоминание (`STACK_DATA.backupStatus / touchBackupMeta`).

Резервная копия (v29.76): файл «Скачать копию» (бывш. «Резервная копия» / «Экспорт») —
`{format:'stack-full-backup', version:1, state, storage}`; `storage` содержит
сырые строки **всех** ключей `stack_*` (кроме кэша курсов `stack_fx_cbr_v1`).
Писать/читать только через `STACK_DATA.exportFull / isFullBackup / importStorage`
(`stack-data.js`). Новый `stack_*` ключ попадает в копию автоматически, если
его имя подходит под `^stack_[a-z0-9_-]+$` — не называть ключи иначе. Импорт
принимает и старый формат (голый `state`).

Календарь процессов: `state.months[i]` ↔ `MONTHS[i]` (`index.html`), индекс 0 =
август 2026. `MONTHS` только **дописывается в конец** (`extendMonthsTo`) — индексы
и данные существующих месяцев не менять и не пересобирать с нуля; длина
состояния важнее текущей даты (его месяцы никогда не усекаются).

Лимиты при загрузке/импорте (`migrateStoredState`, `validateImportedState`)
не должны быть ниже того, что принимает интерфейс: тихая обрезка = потеря
данных (так терялись новейшие задачи свыше 1000 и длинные заметки).

Не создавать новые дублирующие ключи без причины.

## Логика статусов процесса

Статусы: `✓` выполнено, `○` пропущено/не выполнено, `—` не требовалось,
пусто — не отмечено.

Цикл: `пусто → ✓ → ○ → — → пусто`

Формула выполнения: `✓ / (✓ + ○)`. `—` и пустые значения в проценте не
участвуют. Если у всех процессов дня `—` — нельзя показывать ложные 100%.

Единственная реализация правил — `validMark / activeCompletion / cycle` в
`index.html` (v29.83); `v22.2.js` больше не подменяет их на лету. Старая отметка
`◐` (частично) осталась только в данных, написанных трекером до v29: она читается
при загрузке/импорте (данные не терять), считается за 0,5 (проценты истории не
меняются), по тапу переходит в `○`, но новые `◐` не пишет ни один экран. Формулу и
цикл менять только в `index.html`, не копировать в другие модули.

## Экран «Сегодня»

Самый простой экран приложения: максимум 1 главное число, 1 вывод,
1 основное действие, максимум 3–4 вторичных блока.

- Показывать актуальные действия; строку нельзя убирать только потому, что
  процесс «не требовался» (`—` остаётся видимым).
- Статус меняется отдельным контролом справа — не путать с навигацией.
- Тап по названию действия открывает соответствующий раздел (например,
  «Тренировка» → Fitness, задача → Дела).
- Просроченные задачи (`due` в прошлом, не «Готово») показываются сверху с пометкой
  «просрочено · N дн.»: максимум 5, остальное — строкой «Ещё N просроченных» → Дела.
  Отмеченная здесь просроченная задача остаётся на экране, пока не уйдёшь с «Сегодня».
- У открытой просроченной задачи справа кнопка «Перенести» (44px): шторка «Сегодня / Завтра /
  Другая дата». Меняется только `due` (и плановый `date`, если он «сегодня»), статус и остальное
  не трогаются (`STACK_DATA.rescheduleTask`). У процессов её нет.
- Снятие отметки с задачи возвращает прежний статус («В работе»), а не «Не начато»
  (`prevStatus` в самой задаче — необязательное поле, импорт его принимает) — и на «Сегодня», и
  в «Дела»: одна реализация `STACK_DATA.toggleTaskDone`.
- «осталось» = ещё не отмечено; пропущенный день (○) в «осталось» не входит — он «пропущено».
- «Тренировка» распознаётся по слову в названии процесса: `STACK_DATA.isWorkoutName`
  (только процессы, не задачи; «Паспорт», «Залог» — не тренировка). Не дублировать
  регулярку в других модулях.
- Экран перерисовывается один раз на изменение (`scheduleToday`), при возврате в
  приложение (`visibilitychange`/`pageshow`) и в полночь; зоны нажатия ≥ 44px.

## Fitness

Главные вкладки верхнего уровня: **Сегодня / Прогресс / Питание**.
«Программа» и другие технические вкладки не должны быть на главном уровне.

Календарь программы (v29.80): номер недели, год программы и фаза берутся только
из `STACK_DATA.programPosition(date)` (`stack-data.js`) — не считать неделю
локально и не заводить свою дату старта. Год 1 = недели 1–52 (Адаптация →
Закрепление), каждый следующий год = 44 недели с недели 9 (без повторной
«Адаптации»). Дата старта — `programStart` в существующем объекте цели
(`stack_fitness_goal_v2318`), по умолчанию 2026-08-10; программа вычисляется
из даты, поэтому смена старта ничего не дублирует, а отметки/подходы
привязаны к календарным датам. Годовая цель тренировок — `yearWorkouts` там
же; «выполнено» = дни со статусом ✓ за календарный год
(`STACK_DATA.yearWorkouts / yearGoal`). Замены упражнений хранятся по блоку
(`block|id`), со 2-го года ключ `y<год>-<блок>|id`.

Не хардкодить дни недели/расписание/workout keys, если их можно прочитать
из текущих данных. Не использовать emoji вроде 🏋 — есть кастомный неоновый
минималистичный workout glyph. Стиль: просто, технологично, немного неоново,
без визуального шума.

Nutrition — порядок обязателен:
1. Моя цель
2. План / факт
3. Рацион
4. Добавить еду

Не создавать параллельные replacement-карточки для Nutrition — улучшать
существующие блоки.

## Раздел «Дела»

Вкладки: **Задачи / Процессы**. Если сверху уже есть вкладки — не дублировать
навигацию кнопками «Все задачи» / «Все процессы», убирать такие кнопки.

Создание задачи — компактный `+`, без большой кнопки «Новая задача».

Список задач (v29.88) — группы по сроку: Просрочено / Сегодня / Завтра / На этой неделе / Позже /
Без срока, внутри — по дню, затем по приоритету. «Готово» — одна свёрнутая группа (по 20 штук).
Правила групп — только `STACK_DATA.taskBucket` (просрочено = открытая задача с прошедшим `due`;
задача без срока никогда не «просрочена»). Тап по галке меняет только свою строку — список
игнорирует собственные `save()` (иначе строка улетает в «Готово» и перерисовывается всё). Даты —
словами (`STACK_DATA.formatDay`), не `2026-10-09`.

Карточка создания/редактирования: одинаковая ширина input/select/textarea,
`box-sizing: border-box`, без горизонтального overflow, одинаковые отступы и
высоты контролов, grid с `minmax(0,1fr)`, чек-лист не должен разъезжаться,
кнопки снизу не должны выходить за экран.

## Финансы

Основной экран: сколько накоплено, сколько за месяц/план, свободная сумма,
`+ Операция`, Цели. История/аналитика/годовые данные — вторичный уровень.

## Аналитика

Основной уровень: общий STACK Score, доменные оценки, главный вывод,
направление/тренд. Не превращать в технический экран — экспорт, импорт,
backup и технические данные вторичны.

Оценки доменов (v29.89) считаются по окнам, не «за всё время»:
- Процессы — календарные 14 дней и 14 до них (`STACK_DATA.processStats`), формула только
  `activeCompletion` из `index.html` (◐ = 0,5). Нет отметок в окне — «нет данных», не 0%. Серия —
  по дням (пропущенный день обрывает, «—» и дни вне расписания нейтральны).
- Задачи — `STACK_DATA.taskStats`: срок за 14 дней + любые открытые со старым сроком (долг);
  будущие и без срока не считаются.
- Финансы — скользящие 30 дней против плана (`STACK_FINANCE.rolling`), не календарный месяц;
  нет ни одной операции — нет оценки.
- Нет данных в прошлом окне → нет тренда (а не «+N» от нуля).
Графики «история» рисуются в реальных пикселях (`viewBox` = размер на экране, подписи 10–11px);
месяц без данных — пропуск, а не 0%.

## Design system

Тёмный, чистый, технологичный, лёгкий neon, минимум декоративного шума.

Не делать: кислотные кнопки повсюду, много разноцветных полос, огромные
карточки без смысла, UI ради UI.

Предпочитать: компактные иконки, чёткую типографику, единую сетку, единые
радиусы и отступы, понятные интерактивные зоны.

## Mobile-first

Главный сценарий — телефон. При ЛЮБОЙ ширине страницы больше 720px (компьютер, планшет,
телефон в ландшафте) `index.html` показывает то же мобильное приложение в рамке шириной
телефона (`index.html?frame=1`; v29.69 — мышь, v29.84 — любое устройство: решение о рамке
принимается сразу после `<meta viewport>`, где `innerWidth` уже верен, а до него телефон
сообщает 980; страница, ставшая шире при повороте, перезагружается в рамку). Старый
широкий интерфейс не показывается нигде — до v29.84 он появлялся на планшетах и при
повороте телефона. Код приложения внутри рамки всегда видит `innerWidth ≤ 720`.
Legacy-разметка `index.html` остаётся источником данных/сохранения; легаси-«Сегодня»,
его рендер и старая нижняя навигация удалены (v29.84), проверка попиксельная.
Проверять как минимум: ширина 390–430px,
отсутствие горизонтального overflow, safe-area, нижнюю навигацию, модальные
окна, textarea/select/date inputs, длинные названия, большие данные.
Интерактивные зоны — удобные для пальца.

## Service worker

При изменении shell/критического JS: увеличивать `BUILD`, менять `CACHE`
name, следить, что новый файл попал в precache/script list — иначе
пользователь получит старый JS из кэша.

Всё, что должно меняться вместе, меняется одной командой:
`node scripts/bump-version.js 29.86 short-name` (`sw.js` BUILD/CACHE,
`stack-persistence.js` VERSION, `stack-v29-shell.js` BUILD, `?build=` у v29-скриптов в
`index.html`). `scripts/stack-verify.js` падает, если эти места разошлись или
пропали иконки/precache. Новый файл в `SCRIPT_PATHS` добавлять вручную.

Как работает SW (v29.85): сеть-сначала, но файлы **перепроверяются**
(`cache:'no-cache'` → 304 без загрузки), а не скачиваются заново (`no-store` тянул
~45 файлов на каждый запуск). Через `NETWORK_TIMEOUT` (4 с) отдаётся копия из кэша,
запрос при этом дорабатывает и обновляет кэш — плохая сеть не держит экран-заставку.
Активация новой версии перезагружает только **скрытые** окна; видимое окно страница
перезагружает сама, когда его скрывают (`controllerchange` в `index.html`), чтобы не
потерять черновик. Иконки: `icon.svg` + PNG (`scripts/make-icons.js` их пересоздаёт);
iOS не читает SVG для `apple-touch-icon`.

Нельзя советовать пользователю первым делом «очистить данные приложения».
Допустимо: полностью закрыть/открыть приложение, обновить/unregister service
worker через DevTools. Не очищать Local Storage без необходимости.

## Startup

Новый shell должен владеть первым кадром — старый интерфейс не должен
показываться перед новым. Нельзя маскировать через новые `setTimeout` или
чинить startup поздними `MutationObserver`.

Если startup ломается, проверять по порядку: синтаксис `stack-v29-shell.js`
→ service worker → build query → порядок загрузки скриптов → снимается ли
startup gate.

**Критический прецедент**: в v29.3 приложение переставало открываться из-за
синтаксической ошибки в тернарном выражении. После КАЖДОГО изменения JS
обязательно: проверять синтаксис (`node --check <file>`), по возможности
запускать приложение локально, искать runtime errors, проверять основные
сценарии. Никогда не отправлять JS без синтаксической проверки.

## Как работать с задачей

1. Изучить код — не угадывать селекторы/storage key/функции, искать через
   grep/поиск: реальный DOM, source of truth, функцию сохранения, текущий
   CSS, текущую бизнес-логику.
2. Найти причину, не лечить симптом, если можно исправить источник.
3. Минимальное изменение — не переписывать полпроекта ради одной кнопки.
4. Не ломать данные — UI менять свободно, state/storage — осторожно.
5. Проверить результат: синтаксис, отсутствие очевидных runtime-ошибок,
   mobile overflow, основной сценарий, назад/вперёд, status toggle,
   service worker build. Для headless-проверки сначала запускать
   `node scripts/stack-verify.js` (обходит все 5 разделов + вкладки
   Fitness, проверяет overflow/JS-ошибки/DOM-churn, плюс сценарии: цикл
   статуса в «Сегодня», синхронизация тренировки, модалка цели Fitness,
   «Поел» → план/факт, замена приёма, точность рациона, полный бэкап
   «экспорт → импорт», локальная дата ночью, отсутствие тихих обрезок
   данных) — не писать
   одноразовый Playwright-скрипт с нуля, если этот чек-лист уже покрывает
   нужный сценарий; для остального (специфичные сценарии конкретного
   бага) — обычный одноразовый скрипт всё ещё нормально.

   Порядок проверок (v29.86), от быстрой к медленной:
   `node --check <файлы>` → `node scripts/stack-unit.js` (секунда: данные,
   миграции, проценты, бэкап — без браузера) → `prettier --check "*.js"
   "scripts/*.js"` (чинится `--write`; index.html не форматируется) →
   `node scripts/stack-lint.js` (только реальные баги: неопределённые имена,
   дубли ключей…) → `node scripts/stack-verify.js`. То же самое делает CI.
   Новая логика данных — сначала юнит-тест в `stack-unit.js`; новый видимый
   сценарий — в `stack-verify.js`. После изменения JS:
   `node scripts/bump-version.js 29.91 short-name`. Быстрый цикл по одному экрану:
   `node scripts/stack-verify.js --only=today,deals,analytics,crud,program,data,sw` (любой набор).
   При удалении «мёртвого» UI — попиксельное сравнение экранов до/после
   (одни данные, фиксированная дата), а не «на глаз».

## Git workflow

Ветка: `stack-v29-x-<short-name>`.

Порядок: обновиться от `main` → создать branch → внести изменения → проверить
diff → проверить синтаксис → закоммитить → создать PR → проверить mergeable
→ squash merge в `main`.

Не пушить хаотичные временные файлы. Не оставлять `_noop`, debug-файлы,
test garbage, закомментированный мусор.

### Перед merge обязательно проверить

- `git diff main...HEAD`
- нет случайных файлов
- JS проходит `node --check`, `stack-unit.js`, `stack-lint.js`, Prettier
- новые файлы подключены (script tags / precache)
- SW build изменён, если нужно
- cache name изменён, если нужно
- storage schema не изменена случайно
- UI работает на mobile, нет horizontal scroll

## Формат ответа после выполнения

Коротко: что было не так → что исправлено → какие файлы изменены → версия →
PR → merge commit. Без длинного отчёта.

Пример: «Исправил. Причина была в X. В v29.5 сделал Y и Z. Данные не менял.
PR #27, merge commit abc123.»

## Главный принцип

Не добавлять новые фичи, пока текущая архитектура не стала простой и
стабильной. Сначала: ясность, стабильность, единый shell, единые данные,
чистая навигация. Потом — новые возможности.
